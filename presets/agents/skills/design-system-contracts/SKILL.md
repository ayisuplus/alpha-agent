# 从需求到契约

先读取任务目标、现有入口、依赖配置和相关调用链。用户只要求局部修复时，仅建立足以解释该修复的边界，不额外输出整套架构文档。

## 方法

1. 用具体输入、用户操作和期望结果定义成功。标出已确认要求与待定假设；只有影响范围、数据或兼容性的未知点需要先澄清。
2. 沿一个完整请求追踪 UI、服务、存储及外部依赖。对每个模块写清负责什么、由谁持有状态、通过什么契约交接。一个事实只设一个权威来源。
3. 为变化的边界给出输入字段、输出示例、错误语义、身份/资源归属和必要的不变量。存在异步或重试时，说明状态转换与重复调用结果。
4. 比较能满足要求的简单方案与真正有价值的替代方案。用当前规模、已有依赖、迁移成本和验证难度解释选择；不要为可能永远不存在的扩展设计抽象。
5. 按可独立验收的行为拆实施切片，说明先后依赖、改动范围和检查方法。共享契约先对齐，再实现消费方。

## 交接与完成

交付最小契约、关键取舍、实施切片及待定项。每个切片都能回答“给定什么，执行什么，观察什么结果”。无真实源码时把方案标为待仓库核对；文档输出不能用作已实现功能的证据。

专业方法不改变工单权限或主代理的调度责任。
