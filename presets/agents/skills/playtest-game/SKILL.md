# 从可玩构建到可信结论

先读设计文档（核心循环、数值表、关卡结构与反馈契约）、可运行构建、目标平台与已有反馈。先把"达标"翻译成可观测信号，再开始试玩；不接受"感觉挺好玩"这类结论。

## 一、定义信号

为每个验收点给出可测指标：通关率与尝试次数、单局时长分布、死亡与失败点分布、资源曲线、关键机制使用率、卡关率、帧时间分布。指标口径写清统计单位与样本量，跨平台或跨版本比较时先对齐口径。

## 二、冒烟与功能

1. 冒烟：能构建、能进入、能完成一次完整循环、能存档读档、无阻断性崩溃；任一不过就停止后续测试并回报。
2. 状态切换：暂停、失焦、结算、重开、退出返回菜单；切换后时间、音频、输入与 UI 不残留。
3. 边界与极端输入：零资源、负值、超大数、连点与多键并发、手柄断连、窗口极端尺寸；随机使用固定种子保证可复现。

## 三、平衡与难度

1. 按设计数值表逐项核对实测：产出、消耗、时间常数与理论收支表是否一致，偏差多少。
2. 主动找退化策略（无限刷、无脑重复、跳过内容的最优解）与无效内容（无人使用的机制与道具），记录触发条件与收益量级。
3. 难度曲线：按失败点分布找聚集位置，判断是难度峰值还是设计缺陷；区分"难而公平"与"难而迷惑"，看不懂的失败要单列。
4. 新手有效性：首次接触的前几分钟是否理解核心操作与目标；教学缺失比难度过高更该优先修。

## 四、手感与性能

1. 手感：输入延迟、命中判定是否与动画一致、镜头跟随与震动是否干扰操作；给出可复现的操作序列与主观描述分离记录。
2. 性能：帧时间取分布而非平均值，标注 p50/p95、掉帧场景、加载耗时、长时间运行是否内存增长；写明设备、分辨率、运行时版本与采样场景。
3. 样本不足或未覆盖的平台标注"未验证"，不给结论。

## 五、记录、定级与回归

1. 每条问题写清复现步骤、环境、期望与实际、证据（日志、实测数字、截图或录屏的采集条件），并按阻断、主要、次要、体验建议定级。
2. 平衡调整建议给出方向、幅度与预期影响，交系统设计专家确认后再改数值，不擅自改设计意图。
3. 修复后按同一清单复跑，记录回归结果与仍未通过项；不承诺留存、付费、评分与上线表现。

## 交付与边界

交付试玩报告（信号表、缺陷清单与严重度、平衡建议与优先级）、复现步骤或随机种子、性能实测表、复测结果。实现修复回到程序工程师，表现层问题回到美术与 UI 专家，自动化基建可与测试与代码审查专家协同；不替实现方决定修法。
