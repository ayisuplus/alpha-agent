# 短视频平台增长（抖音 / 快手）

## 适用范围

- 账号定位与人设、赛道选择、对标拆解、选题与发布节奏、标题文案与话题标签、评论区运营、流量诊断和起号/破池方案。
- 抖音与快手分开对待：抖音以内容推荐和兴趣电商为主、节奏快；快手更看重熟人感与"老铁"信任、私域复购强，方案语气和互动方式单独调整。

## 原则与边界

- 用一条作品的真实留存曲线判断问题出在钩子、节奏还是信息密度，而不是笼统地说"内容不行"。
- 尊重平台机制，厌恶标题党、硬悬念和养号玄学；只奖励真正被看完、被收藏、被回访的内容是长期方向。
- 人设优先用真实经历、真实场景和可验证的专业身份建立信任；不编造身份、资质与成果。
- 平台权重、阈值和活动规则有时效性且口径众多（例如完播、收藏、回访的权重排序、长效赛马的观察窗口），只把它们当作需要核实的假设：动手前查抖音创作者服务中心、巨量算数/巨量学、快手创作者服务平台等官方或真实页面并注明核对日期；创作者经验数据与官方口径分开标注。
- 不提供刷数据、搬运、伪原创或规避审核的方法；账号操作、投流与发布需当前授权，不承诺播放、涨粉与成交结果。

## 一、定位与起号

1. 确定赛道、目标人群和内容价值：一条账号只承接一个清晰人群和一类需求，赛道不摇摆。用一句话写清"我是谁、给谁、解决什么、凭什么是我"。
2. 设计账号四件套：名称＝领域＋细分场景/记忆点；头像用真人或领域标志；简介按"专注领域＋提供价值＋互动/信任引导"；背景图补充成果或承接方式。
3. 找对标：优先研究平台榜单中粉丝量不大但近期快速起量的账号（如抖音新势力榜、快手潜力榜），而非只看头部。逐项拆解其选题、开头 3 秒、结构、字幕画面、结尾引导、标签与更新频率，借鉴方法不照搬内容。

## 二、内容与发布

1. 短视频结构以"钩子 → 价值展开 → 行动引导"为骨架，知识/带货类可用 S.T.A.R.T.（承诺与前提 → 不行动的代价 → 步骤/演示 → 结果对比 → 下一步引导）。
2. 开头极短：第一时间抛出痛点、结果、反常识结论或具体冲突，不铺垫自我介绍；一条视频只讲清一个点，每数秒给一个新信息点，字幕与画面承担无声播放场景。
3. 标题写具体对象＋结果/冲突，不用空泛副词；话题标签以垂直精准为主、热点标签为辅。BGM、画面节奏与平台当下内容形态保持协调，趋势类元素先看真实热榜确认。
4. 固定更新节奏，发布时间对照目标人群的活跃时段（以后台数据为准，不迷信统一"黄金时段"）。发布后首小时积极回复带问题和观点的评论，用置顶评论补充信息或引导讨论。
5. 快手方案单独调整：强化真人感、熟人语气和连续直播/私域互动，内容可更朴实完整，不套用抖音的快剪与强钩子。

## 三、诊断与迭代

1. 沿漏斗定位：曝光不足看定位与标签承接；点击不足看标题/封面/开头；留存不足按播放进度曲线找到集中划走点，改对应段落；互动不足看内容是否值得评论/收藏；涨粉不足看是否有持续关注价值；转化不足看人群精准度与承接路径。
2. 以平台后台真实数据为准（创作者服务中心、电商罗盘、快手创作者服务平台等），第三方工具（巨量算数、蝉妈妈、新榜等）数据标注为估算。所有阈值（如 3 秒留存、完播、互动率门槛）只作参考线索，先核实当前官方口径再使用。
3. 平台已从短期爆发转向更长周期的持续赛马，优质但起步平淡的干货内容可持续观察其收藏、回访与深度评论，不因首日数据普通立即放弃；同时避免对单条爆款做过度归因。
4. 每轮迭代只改少数变量并记录假设，形成"发布 → 诊断 → 假设 → 验证"的闭环；跨条统计与周期复盘按 `review-content-analytics` 的方法展开。

## 工具用法

- 调研与核对：用 `web_search`/`fetch` 查官方规则中心、创作者学院与真实榜单页面，记录链接与核对日期；需要登录后台查看数据时用 OMP 原生 `browser`（需用户授权，可访问本机开发服务器）。
- 素材制作：封面/视频素材用 `alpha_generate_image` / `alpha_generate_video`，产出写到 `outputs/media/<可读名>.<扩展名>`；ComfyUI 服务不可用时上报缺口，不代替用户启动服务。
- 发布包与方案文档用 Markdown 交付，或用 `alpha_office create`（Markdown→docx/pdf、表格数据→xlsx）写入项目内 `outputs/`，之后用 `preview` 自检；工具返回 `{ summary, artifacts: [{ path, kind, sha256, preview? }] }`。
- 限制说明：不代用户发布、投流或操作账号；后台数据读取不到时如实上报缺口，交付数据需求清单，不虚构账号表现。

### 浏览器自动化

浏览器自动化用 `eval` 的 `browser` 命名空间（同一可见浏览器，保留登录态；首次使用会询问会话级授权）：

- 打开与读取：`await browser.open({ url })` 打开页面，`browser.tabs()` 列标签；读页面内容优先 `await tab.extract("markdown")`，看结构用 `tab.ariaSnapshot()`。
- 稳定操作：先 `await tab.waitFor(selector)` 等元素出现再操作；点击与填表优先用**元素句柄**——`const el = await tab.waitFor("#go"); await el.click(); await el.fill("文本")`——或用稳定选择器（id、角色、可见文本），不做坐标点击。
- 键盘与滚动：`tab.press(key)`、`tab.type(selector, text)`、`tab.scroll(dx, dy)`；等待跳转后重新 `waitFor` 目标元素。
- 每步操作后读回 DOM 或元素文本核对结果，不以“没报错”当成功；需要留证时 `await tab.screenshot()`。
- 表单提交、发布、后台写操作必须先获得用户明确授权；授权弹窗按“仅这次 / 本会话 / 拒绝”如实选择，不绕过、不代答。

## 交付与边界

交付定位方案、对标拆解、选题库、作品发布包（标题/文案/标签/封面简报）、诊断结论与下一步实验清单。标注待核验事实、待授权素材和未执行项。营销/AI/演绎等标注问题按 `check-content-compliance` 的清单核对。
