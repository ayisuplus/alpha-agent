# 可落实的交互设计

## 适用范围

- 用户流程、页面结构、组件状态、响应式和可访问性规范；界面验收情境的编写。
- 输入是用户要完成的事情、现有页面/组件、品牌资料和已批准的需求；优先查看实际界面，图像未看过、网页未打开时不描述其具体设计。

## 原则与边界

- 先关心人能否顺利完成操作，再判断界面是否漂亮；从真实优质案例提取信息层级、布局和交互原则，不用"高级感"一类空泛形容词。
- 品牌、素材和文案权威以用户资料为准，不凭参考图改掉身份或产品定位。
- 涉及审美方向时先找真实优质案例，记录 URL 或本地路径、查看日期、具体借鉴维度；不把参考的品牌、人物或内容挪作用户产品。
- 已有设计系统优先复用；只为当前流程需要的内容规定层级、间距、文字、色彩语义和交互，不凭空搭建组件库。
- 没有可查看的页面或参考时说明待验项，不假称做过视觉审查；不擅自改变接口或增加功能。

## 参考与方案

- 将关键路径画成状态和动作：进入、填写、提交、加载、成功及实际可能发生的失败。区分空数据、无权限、请求失败；重试后的输入和焦点应有明确去向。
- 小屏、键盘和较长内容下检查主要动作是否仍可达。控件用语义、可访问名称、焦点顺序和明确反馈表达行为，而非只靠颜色。
- 文案写清每个状态的可观察反馈：按钮可用/禁用条件、加载提示、错误信息指向下一步动作。

## 交付给实现方

- 交付页面/组件、状态、动作、文案和验收情境；注明参考、复用项及新增项。验收情境写清"给定什么状态，做什么操作，观察到什么结果"。
- 若提交原型，说明哪些操作是真实逻辑、哪些只是展示。服务不可访问时交付待实现规范，不替换用户指定工具。

## 验收

- 用实际渲染页面检查关键路径、布局与键盘操作，记录尺寸和结果。只有截图不能证明交互通过；只有 DOM/构建检查不能证明视觉质量。
- 局部文案或样式修复按影响范围验证即可；验证方法与结果一并记录，待验项明确列出。
