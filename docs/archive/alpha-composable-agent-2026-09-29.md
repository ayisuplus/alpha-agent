## 0. 定位与价值

现在的智能体产品大多是"一个强模型加一个主循环"（Claude Code、Codex 这一类），上限由单个模型决定。Alpha 要走另一条路：**摸一摸"专家加模型组合"的上限。**

一句话定位：**Alpha 是智能体工作的 ComfyUI。**

| ComfyUI | Alpha |
|---|---|
| 每个节点选不同的模型、LoRA、参数 | 每个节点选不同的专家、模型、工具 |
| 高手能搭出远超默认效果的工作流 | 专家质量越高、模型搭配越得当，上限越高 |
| 工作流可以保存、分享，普通人直接套用 | 专家包和流程模板可以保存、分享、复用 |
| 不绑定任何一家模型 | 继承了内核的多家厂商接口，不绑订阅 |

三条价值主张：

1. **专家可以沉淀。** 把平台规则、合规要求、内容格式这类行业经验做成可版本化、可分享的专家包。价值随专家库增长，而不随某一家模型厂商涨落。
2. **模型可以自由组合。** 每个节点挑最合适、最便宜或者当下能用的模型。2026-09-29 评测期间 xiaomi 限速、额度将尽，直接改用 deepseek 继续跑，这就是不绑订阅的实际价值。
3. **高手搭建，普通人复用。** 上限由高手拉高，普通用户用他们分享的默认配置和模板。

"上限高"目前还是判断，不是结论。第 8 节的对比实验负责把它变成数字；实验不成立时的退路见第 10 节。

## 1. 设计原则

| # | 原则 | 含义 |
|---|---|---|
| P1 | **智能体居中，运行时做操作系统** | 运行时提供资源、隔离、权限、状态、上下文和缓存服务，不替模型决定下一步做什么。不再设计"公司式"的常设角色（规划者、会议、运维） |
| P2 | **两种模式** | 智能体模式是默认，处理临时任务；组合模式按用户或专家设计的流程图执行。流程是智能体手里的工具，不是系统骨架 |
| P3 | **专家是一等公民** | 专家包可以版本化、评测、分享、组合；专家按需装载、离开就卸载，不进主池 |
| P4 | **模型自由** | 可以按节点、按回合选模型；有能力档案做校验和推荐；不绑订阅 |
| P5 | **缓存与前缀稳定是硬约束** | 凡是改写上下文的地方，都用确定的运行时规则，只改尾部，不回头改历史 |
| P6 | **先计划后行动，但计划要轻** | 写工具在计划记录之前仍被拒绝；计划是承诺和路线图，智能体模式下不由运行时逐步强制执行 |
| P7 | **治理要硬、要薄、放在边界** | 权限、预算、对外产物的独立 gate、审计由运行时强制；其余交给模型 |
| P8 | **"模型强一倍"检验** | 每个部件都问一句：模型强一倍后，它更有用还是更多余？更多余的就是给弱模型搭的脚手架，必须能拆、默认从简 |

## 2. 现状诊断（为什么要改）

1. **主代理只活在 `alpha_plan` 那一步。**
   - 进入节点后，协调者会话被注入专家人设（[session-profile.ts:265](../../src/runtime/session-profile.ts)），换专家就中断本轮、重建会话（[omp-runner.ts:391](../../src/runtime/omp-runner.ts)）。
   - 下一个节点、专家、审查者都由运行时决定（[omp-runner.ts:283](../../src/runtime/omp-runner.ts)）；续跑靠 driver 写死的催促语（[runs.ts:203-290](../../src/server/runs.ts)）。
2. **卡在中间状态。** 运行时在做决策，却要求模型自己记账：调 `alpha_plan`、`alpha_step`，算哈希，修订计划。F1–F12 这 12 个缺陷里有 6 个是"图没推进，运行时再推一把"。
3. **评测数据**（附录 B）：
   - `sales-question` 从 1 轮变成 4 轮；
   - `stale-premise` 16–17 轮、修订 8 次、千万级 token；
   - 回边和返工只在把要求写进 objective 的演练里出现；
   - P0 与 P6 用的模型不同，"图化是否提高通过率"目前没有答案。
4. **重点方向受限。** 内容任务不能派发子代理（[cognition-tool.ts:93](../../src/runtime/cognition-tool.ts)）。
5. **模型选择只到任务级。** 已有任务级 `modelSelector`、工单级 `modelSelector` 和设置里的厂商白名单（[model-policy.ts](../../src/runtime/model-policy.ts)），还没有节点级、回合级的选择，也没有能力档案。

## 3. 目标架构

```
┌──────────────── 资产层（可沉淀、可分享）────────────────┐
│  专家包（人设 + Skill + 交接声明）  流程模板  模型能力档案  │
└───────────────────────────────────────────────────────────┘
┌──────────────── 智能体层 ─────────────────────────────────┐
│  主线对话（常驻智能体）── 叠加层：节点人设 / 主方法 / 工具  │
│        └─ 分支：子代理 / 独立审查 / 流程运行（带工作区）    │
└───────────────────────────────────────────────────────────┘
┌──────────────── 运行时层（操作系统服务）──────────────────┐
│ 权限与审批 · 预算与中断 · 上下文组装与缓存 · 事件日志与恢复 │
│ 隔离（worktree / 沙盒）· 对外 gate · 模型路由与档案校验     │
└───────────────────────────────────────────────────────────┘
```

### 3.1 智能体模式（默认）

- **主线对话**：一个任务一个常驻智能体，全程在场，负责计划、判断、处理中断、和用户对话。
- **节点叠加层**：进入节点时，运行时追加一条"节点头消息"（专家人设、主方法、节点简报、本节点可用的工具），并切换工具守卫；用 `alpha_step` 退出时，交接记录就是这个节点的"提交说明"。同一个对话里可以接连执行多个节点，只换人设和工具。
- **分支**：只在需要隔离时开：
  - 并行工作；
  - 在 worktree 里改代码；
  - 对外产物的独立审查（审查分支只拿交接记录和产物，不带主线历史）。

  分支结束后通过 `alpha_integrate` 和交接记录合并回主线。
- **中断**：运行时检测到异常时，把一份统一格式的"事故单"发给主线智能体，由它处理。异常包括：驱动报错、违反任务不变量（[task-invariants.ts](../../src/runtime/task-invariants.ts)）、图卡死、连续没有进展、超出预算。智能体也处理不了，才找用户。**不设单独的运维角色。**
- **计划**：先计划后行动，但计划很轻。小任务可以只有一个节点，或者直接回答。三阶段骨架在这个模式下不强制。

### 3.2 组合模式（上限所在）

- **流程模板**：由用户或专家设计、保存、分享的流程图（格式见 4.3）。每个节点预先设定专家、模型、工具、工作区、会话分组、目标、预算和上报规则。
- **启动方式**：智能体把"运行流程 X、输入 Y"当作一个工具调用；也可以由用户直接启动。
- **执行**：由运行时按模板推进。这里复用现有计划图的机制：生命周期、交接、gate、回边、输入过期。异常按 3.1 的规则中断给主线智能体。
- **沉淀**：一次智能体模式跑得好的任务，可以"存为流程模板"。这是把高手的做法变成普通人能复用的资产的主要途径。

### 3.3 用户参与点

- **开工前**：审阅计划或流程、预估成本，并**一次性预先授权**需要的命令、外部动作和预算。评测里最常见的暂停原因是执行中的命令审批，预授权把它前移到开工前。
- **执行中**：随时可以和主线智能体对话；没有预授权的动作、不可抗力、需要决策的中断，都由智能体带着"摘要 + 可选动作 + 建议"来找用户。
- **交付时**：验收，或者要求返工。
- 现有各处 `needInput` 调用，按 [pause-reasons.ts](../../src/runtime/pause-reasons.ts) 的原因代码逐一映射到上面三个参与点。

### 3.4 被降级为工具的想法

讨论中提出过的"公司式"角色，一律改成智能体可以调用的工具：

| 原想法 | 落地方式 |
|---|---|
| 规划者用更强的模型 | 回合级模型路由：规划回合用"规划模型"（用户可选），执行回合用节点模型 |
| 多模型开会 | 工具 `alpha_second_opinion`：请另一家模型按清单评审方案，意见和分歧附在计划上给用户看。高风险任务可以默认调用一次 |
| 运维兜底 | 运行时中断加事故记录：同一类事故反复出现，就修运行时，不靠手动补丁 |

## 4. 资产层

### 4.1 专家包

- 结构沿用现有规范（AGENTS.md §3）：人设 + `SKILL.md` + `index.json` 注册的 `mounts` 与 `handoff`。
- **质量要可衡量**：每个内置专家配一小组"黄金任务"（固定输入、评分标准、必须拦下的问题），专家改版时回归一次。高上限靠的就是高质量专家。
- **时效性**：平台规则、算法口径必须标注核对日期和来源性质，沿用 AGENTS.md §3。
- **分享**：基于 [expert-package.ts](../../src/runtime/expert-package.ts) 做导入导出，内容哈希计入版本。

### 4.2 模型能力档案

每个可用模型一份档案。凡是能测的项，都用 [scripts/probe-model.ts](../../scripts/probe-model.ts) 扩展出来的探针实测，并记录日期：

| 字段 | 用途 |
|---|---|
| 工具调用可靠性（实测） | 需要调用工具的节点，拒绝或警告不合格的模型 |
| 上下文长度 | 校验节点的输入规模 |
| 是否支持缓存、缓存价格 | 成本估算；换模型会断缓存的提示 |
| 语言和领域特长（实测加人工标注） | 默认推荐，例如中文写作 |
| 价格 | 开工前的成本预估 |
| 可用性（厂商白名单、额度） | 选择模型时过滤 |

运行时根据档案校验"节点需求与所选模型"是否匹配。档案是推荐和护栏，不替用户做决定。

### 4.3 流程模板格式

```yaml
flow: douyin-script
version: 1
inputs: [brief, source-material]
nodes:
  - id: research
    objective: 核实素材中的事实与数据来源
    expert: core-researcher
    model: deepseek/deepseek-flash
    tools: [read, alpha_search, alpha_source, alpha_step]
    workspace: mainline            # mainline | worktree:<名字> | sandbox
    session: s1                    # 同一个 session 的节点共用一个对话
    budget: { soft: 100k, hard: 200k }
    produces: [research-notes]
  - id: draft
    objective: 60 秒内口播初稿，事实均引用 research 产物
    expert: core-content-strategist
    model: <用户选择的中文写作模型>
    session: s1
    consumes: [research-notes]
    produces: [script]
    gate: [compliance]
    escalate: { agent: [premise-invalid], user: [budget-hard] }
  - id: compliance
    kind: review
    gateRole: compliance
    session: branch                # gate 一律开分支，保证独立
```

运行时的校验规则，复用现有 `alpha_plan` 的校验：

- 专家、工具、模型、工作区只能从封闭目录里选，缺了就在**开工前**报能力缺口；
- 依赖不能倒挂到更晚的阶段；
- 每个 gate 都要有承担者；
- gate 节点不能和它审查的节点在同一个会话里；
- 同一个会话分组必须在同一个工作区；
- 同一个会话里换专家，必须在节点边界 squash（第 5 节）。

## 5. 上下文与缓存

1. **前缀分层**，越稳定越靠前：

   ```
   [OMP 系统提示词 + Alpha 基础契约]    整个任务不变
   [工具全集]                           开工时确定，节点之间不变
   [任务头消息：目标、验收标准]          任务修订时追加新版本，不改旧消息
   [节点1 头][节点1 → 交接][节点2 头]…   只追加
   ```

2. **易变内容移出系统提示词**：专家人设、主方法、上游交接、用户指导、验收标准、状态快照，一律用 `steer` 追加成消息。
3. **工具全集在开工时算一次**：取计划或模板里所有专家声明的 MCP 和插件的并集；每个节点能用哪些工具由守卫限制（沿用 [file-tool-guard.ts](../../src/runtime/file-tool-guard.ts) 的做法）。`setActiveToolsByName` 只在必须彻底移除某个工具时使用。
4. **squash 由运行时触发**：
   - 只在节点退出那一刻做，把该节点的对话段替换为"节点头摘要 + 交接记录"。这时它是尾部，前缀不受影响。
   - 触发条件：下一个节点换了专家（必须压，这样才算真正卸载），或者这一段超过 N 个 token。
   - 同一个专家连续执行的小节点保留原文。
   - 错过这个时机的段落不再改写，由 OMP 的全局压缩兜底。
5. **按模型分开缓存**：节点之间换模型就断缓存。能力档案在开工前的成本预估里提示这一点；"同一个专家搭配同一个模型"在不同任务之间仍可命中缓存。
6. **技术前提**：OMP 已支持 `steer` 和 `setActiveToolsByName`；"替换历史尾部"的接口尚未确认，R2 第一步先做验证，做不到就退回用压缩接口只保留尾部摘要。

## 8. 证明上限：旗舰对比实验

- **任务**：内容线的真实任务，以 `content-pipeline` 为基础，至少 3 个不同题材，每组跑 2 轮以上。
- **对照组**：
  - A：单个强模型，智能体模式、不挂专家（模拟"强模型加主循环"）；
  - B：Alpha 组合模式，内置专家，每个节点按能力档案选模型，可以混用国产和海外厂商；
  - C（可选）：和 B 相同，但所有节点都用最便宜的模型，用来检验"专家能否弥补模型差距"。
- **指标**：
  - 质量：按评分标准盲评，用户和模型评审各一份；
  - 合规问题被拦下的数量（对照专家黄金任务里的问题清单）；
  - 成本：新 token 加缓存读取、折算价格；
  - 用时；
  - 用户中途被打断的次数。
- **判定**：B 的质量显著高于 A，且成本不高于 A 的 1.5 倍，就算"上限论"成立；C 接近 A，说明"专家可以弥补模型差距"成立。
- **口径**：只报实测数字，不外推传播效果（AGENTS.md §2）。

## 9. 不做的事

- 不设常驻的规划者、会议、运维角色（P1）；这些想法按 3.4 降级为工具。
- 不在智能体模式下强制三阶段骨架或由运行时逐步推进。
- 不承诺未实测的效果；"上限高"在第 8 节的实验之前只是假设。
- 不为了提高缓存命中而限制用户选模型：只提示成本，不做拦截。

## 10. 风险与退路

| 风险 | 应对 |
|---|---|
| 配置负担：大多数用户不懂各家模型 | 能力档案给出默认推荐；内置高质量模板；"存为模板"让高手的做法沉淀下来 |
| 模型兼容性：工具调用质量参差 | 用实测档案校验；不合格的模型在需要工具的节点上给出警告或拒绝 |
| 复杂度回潮，又变回"开公司" | 每个新部件都过一遍 P8 检验；新角色一律先做成工具 |
| 专家质量参差 | 黄金任务回归；专家版本化 |
| 缓存断裂 | 第 5 节的规则；在成本预估里提示 |
| **实验表明 B 并不优于 A** | 价值主张收缩为"不绑订阅 + 对外内容的治理（合规 gate、审计）+ 中国媒体内容专家库"，组合模式保留为高级功能，主要投入转向智能体模式和专家质量 |
