## 0. 结论先行

1. **诊断**：计划做完以后，主代理这个角色实际上就不存在了。节点里的会话换上专家人设，却仍握着主代理的全部工具；编排决策（下一个进哪个节点、用哪个专家、谁来审、是否返工、何时续跑）都由运行时的 driver 做。
2. **方向**：主代理改为贯穿整个任务的**主线对话**（类比 git 主分支），节点默认在主线里执行，只换人设和工具；需要隔离的工作才开**分支**（类比 worktree）。
3. **约束**：所有改写上下文的动作都以缓存命中和前缀稳定为前提；squash 由运行时按固定规则触发。
4. **价值评估**（第 1 节）：这套系统真正不可替代的只有四样硬约束。计划图的大部分运行时强制是否值得保留，先用一次 A/B 评测决定，再定后续施工范围。

## 1. 这套系统值不值得

### 1.1 它到底做成了什么

把整套机制剥开，核心效果确实是：**让模型事先决定什么时候、以什么身份、用什么工具、在什么环境里做什么事**，并把这个决定落成可见、可恢复的记录。

单靠这一点，不值得一个图引擎。强模型加一个主循环（例如 Claude Code：单个主代理、软性的待办列表、Skill 只放描述按需读正文、需要隔离时开子代理、权限和钩子由运行时强制），也能在对话里临时做出这些决定，效果通常不差。

### 1.2 自家评测给出的证据

| 观察 | 数据（附录 B / 施工记录） | 含义 |
|---|---|---|
| 小任务开销上升 | `sales-question`：1 轮 → 4 轮，新 token 基本持平 | 三阶段骨架对小任务是纯开销 |
| 结构本身是主要缺陷来源 | F1–F12 共 12 个缺陷，其中 6 个是"图没推进、运行时只好再推一把" | 引擎越强制，需要的补丁越多 |
| 模型在和结构较劲 | `stale-premise`：16–17 轮、修订 8 次、千万级 token；模型为了交接哈希去跑命令，结果触发审批暂停 | 弱模型没能用好结构，反而被结构拖住 |
| 回边、返工的价值只在演练里出现 | 正式轮 `premise` 回边为 0；premise 回边和合规返工（拦下 5 处广告法风险）是把"先声明回边""初稿必须违规"写进 objective 的演练 | 还没有证据表明结构在自然任务里带来质量提升 |
| 基线不可直接比 | P0 用 xiaomi mimo，P6 用 deepseek-flash | "图化是否提高通过率"目前没有答案 |

### 1.3 值得保留的：强模型单代理给不了的四样硬约束

1. **权限与审批边界**：模型不能自己给自己授权，包括沙盒、命令审批、访问级别、外部动作授权。这一样与计划图无关，本来就该由运行时强制。
2. **高风险产物的独立 gate**：对外发布的内容（广告法、资质、AI 标注）要由独立上下文审查，避免自审放行。这正是项目重点方向（中国媒体内容）的刚需。
3. **可恢复、可审计的任务状态**：长任务、暂停恢复、自动化、工作台展示都依赖事件日志。
4. **上下文卫生**：专家的 Skill 不进主池，激活才装载（用户的解耦初衷）。这一样用主线的"叠加层 + squash"就能做到，不需要每个节点重建会话。

### 1.4 建议降为软约束的

以下内容保留为模型维护、界面可见的计划，但不再由运行时强制：

- 每个任务必须有"调查/执行/审查"三阶段骨架，以及阶段顺序校验、死图检测；
- 由运行时挑选下一个节点、在节点切换时重建会话、driver 的多套续跑机制；
- 非 gate 节点的输入哈希过期、回边次数上限。

"先计划后行动"这个前提保留：写工具在计划记录之前仍被拒绝，这个守卫成本很低。变化只在于：计划是模型的承诺和用户看得见的路线图，不再是运行时逐步执行的状态机。

**这一节是建议，不是结论。** 第 8 节的 A/B 评测给出数据后再定。

## 3. 目标模型：主线 + 分支

| git | Alpha |
|---|---|
| 主分支 | **主线对话**：一个任务一个常驻的主代理对话，底层人设是编排者 |
| 提交 | 在主线执行节点：进入时追加"节点头消息"（专家人设、主方法、节点简报、本节点可用的工具）；用 `alpha_step` 退出，交接记录就是这次提交的说明 |
| 分支 | 需要隔离的节点：gate 审查（独立上下文）、并行工作、在工作区里改代码的子代理。分支从交接记录和产物起步，不带主线的对话历史 |
| 合并 | `alpha_integrate`，加上把交接记录回写到主线 |
| squash | 节点退出时，把这个节点在主线里的那段对话压成它的交接记录（第 5 节） |
| 回到旧提交重做 | `rework` / `premise` 回边 |

主代理的职责自然回来了：节点退出、叠加层撤下之后，说话的还是一直在场的主代理。它读交接、写下一个节点的简报、决定推进、修订、回边还是问用户，并在下一个节点边界回复分支的消息。不需要额外的编排回合，也不需要 driver 的催促语。

计划里的 `host` 取值改为 `mainline | branch`，取代现在的 `coordinator | worker`。gate 审查节点一律为 `branch`。

## 4. 缓存与前缀稳定原则

前缀按稳定程度分层，越稳定越靠前：

```
[OMP 系统提示词 + Alpha 基础契约]   整个任务不变
[工具全集]                          计划批准时确定，节点之间不变
[任务头消息：目标、验收标准]         任务修订时追加新版本，不改旧消息
[节点1 头] [节点1 → 交接] [节点2 头] …   只追加
```

1. **易变内容移出系统提示词**：专家人设、主方法、上游交接（`handoffSection`）、用户指导、验收标准、任务状态快照，一律改成追加的消息（用 OMP 的 `steer`）。
2. **工具全集在计划批准时算一次**：取计划里所有专家声明的 MCP 和插件的并集；每个节点能用哪些工具由守卫限制（沿用 [file-tool-guard](../../src/runtime/file-tool-guard.ts) 的做法）。计划修订引入新 MCP 时缓存断一次，这种情况很少，可以接受。`setActiveToolsByName` 只在必须彻底移除某个工具时使用。
3. **用户中途改目标或追加指导**：追加消息，不重写前缀。

## 5. squash 规则（由运行时触发）

- **时机只有一次**：节点用 `alpha_step` 退出时，运行时把"节点头消息"到退出之间的那段对话替换为"节点头摘要 + 交接记录"。这时它是对话尾部，前面的前缀不受影响。退出时没有压缩的段落，之后就不再改写，只由 OMP 的全局压缩兜底。
- **触发条件**（满足任一即压缩）：
  - 下一个节点换了专家：为了真正卸载上一个专家的人设和 Skill，必须压缩；
  - 这段超过 N 个 token（可配置，初值待评测标定）。
- **不压缩**：同一个专家连续执行的小节点保留原文，下一个节点直接复用已缓存的前缀。
- **技术风险**：OMP 已支持 `steer` 和 `setActiveToolsByName`，但还没确认它有"替换历史尾部"的接口。R2 第一步先做验证；如果做不到，退而求其次，用 OMP 的压缩接口只保留尾部摘要。

## 6. 主代理在主线上的职责

- **节点简报**：进入节点前，由主代理写本节点的简报：从上游取什么、要注意什么、本节点的验收标准。节点不再直接读上游的原始交接记录。
- **返工判断**：`changes-requested` 之后由主代理写返工简报，说明要改哪几处；返工次数上限保留为运行时护栏。`inconclusive` 可以直接转给用户。
- **消息箱**：分支里的 `alpha_send` 发给主线；主代理在节点边界回复、补充上下文，或走回边。
- **最终验收**：仍由运行时根据证据判定，主代理不能自审放行。

| 期 | 内容 | 规模 | 验证 |

| R3 | 分支化：gate 审查节点、`host: branch` | L | 返工演练场景跑通；审查分支的上下文里只有交接记录和产物 |
| R4 | 内容任务开放分支（例如多个平台的版本并行） | M | `content-pipeline` 场景跑通 |

**A/B 的决策规则**：如果 `soft` 的通过率不低于 `hard`，并且轮次或 token 明显更少，就把第 1.4 节列出的运行时强制降为软约束，R3、R4 只围绕第 1.3 节的四样硬约束施工；反之保留 `hard`，按原计划推进。

**总体成功标准**：
- 运行时强制续跑的次数接近零；
- 缓存读取占输入的比例明显高于 round-3；
- 小任务轮次回落到 1–2 轮；
- 合规 gate 在非演练的内容任务上仍然执行。

## 9. 风险与待定

- **人设残留**：同一对话里，上一个专家的文本在压缩前仍在历史中。依靠"换专家必压缩"规则兜底，需要测试覆盖。
- **主线过长**：依靠 squash 控制长度，OMP 全局压缩兜底；全局压缩会断前缀，应当很少发生。
- **弱模型的表现**：主线让主代理承担更多判断，deepseek-flash 这类模型能否胜任，由 A/B 数据回答。
- **待定**：squash 的 token 阈值 N；`soft` 模式下是否仍保留"写工具需先有计划"守卫（建议保留）。
