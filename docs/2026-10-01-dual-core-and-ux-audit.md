# Alpha 双内核接入与界面体验审查 · 2026-10-01

## 结论

OMP 的原生执行链和大部分能力已经保留，天枢也使用了 OMP 的事件、会话与压缩通道。架构方向合理，但“两个内核的有用能力已经充分释放”目前证据不足：OMP 桌面桥存在完成状态与模式恢复缺口；天枢实际只接入七类轻量信号，部分信号的证据与生命周期还有错误。

建议继续让 OMP 独立拥有执行、工具、子任务、审批和会话，把天枢加强为可追溯的诊断与证据建议层。两者通过原生事件合作；Alpha 负责桌面呈现和本机能力。这能保持高内聚、低耦合，并延续已经确认的原生化方向。

审查基线的 UI 问题不只是颜色或圆角：侧栏、主区、输入框主要靠平面填充与细线区分，光源、表面厚度与浮层层级缺少统一表达。用户确认“温润科技＋立体层次”设计后，本轮已落实统一材质、光影与按压反馈，并按追加要求整理侧边栏布局。内核问题本轮交付优化方案，尚未修改执行内核。

## 优先问题与最小优化

### A1 · P1 · 本地命令完成后仍被判定为忙碌

触发：空闲桌面会话提交 `/tools`、`/stats` 等不启动 agent 的命令。

`RpcProcess` 在 [rpc-process.ts:124](../src/native/rpc-process.ts#L124) 为 prompt 加入待完成集合；[响应清理](../src/native/rpc-process.ts#L89) 只处理失败与 `prompt_result/session_settled`。当前 OMP 的本地命令成功响应是 `data.agentInvoked:false`，不再产生 prompt receipt。`startPrompt` 的完成等待也只消费 receipt。

后果：界面可显示“本轮结束”，服务端仍认为有任务；原生会话终端、空闲回收、项目收尾与定时任务完成等待被阻塞。真实隔离界面已复现 `/tools` 后打开 Alpha 终端失败；桥协议探针也得到 `pendingAfterLocalCommand:true`、`completionSettledAfterResponse:false`。

最小优化：把成功本地命令响应作为明确的完成事件，清理 prompt tracking 并结算相应完成 promise。验收覆盖普通 prompt、纯本地命令、异步工具、退出与失败，避免把“接受请求”普遍当作“完成”。

### A2 · P1 · 旧通过证据可掩盖后来失败，命令识别也可能产生假绿

[state.ts:268-295](../src/native/tianshu/state.ts#L268) 在失败分支没有撤销对应验证族的通过记录；成功分支只按命令字符串与 `isError` 判断。探针复现：

| 序列 | 当前观察 | 正确语义 |
| --- | --- | --- |
| 写代码 → 测试通过 → 测试失败 → “测试全绿” | 无宣称问题，验证债为 false | 最新失败不能继续由旧通过背书 |
| `echo bun test` | 识别为测试证据 | 打印命令不是执行验证 |
| `git reset --hard HEAD` | 不算代码变更 | 可能改变验证针对的代码 |
| `git commit -m probe` | 算代码变更 | 仅提交相同文件通常不改变验证对象 |

最小优化：按验证族记录最新尝试及其结果；失败使该族的旧通过失去当前证明力。命令只能提供候选分类，原始执行结果决定测量质量。无法确认的结果标为 `partial`，并纠正 Git 变更分类。

进一步优化：为证据记录会话/分支、目标、文件范围、代码修订、`toolCallId`、执行时间和原始结果定位。局部测试只支撑对应范围的结论。采用可迁移的 snapshot 版本，避免修改历史验收数字。

### A3 · P2 · 待办与宣称的生命周期不准确

当前 [extension.ts:177](../src/native/tianshu/extension.ts#L177) 只消费 `todo_reminder`。实际 OMP 的 `todo-tracker.ts:233-278` 只发送未完成项，全部完成时直接返回。因此“待办全部完成但缺验证”无法在真实事件链触发，已完成项也可能作为未完成内容进入重锚。现有测试手工构造事件，未覆盖这一原生契约。

此外，[state.ts:297](../src/native/tianshu/state.ts#L297) 永久累加成功宣称。已经证明的旧回复在后来写入代码后，会重新变成当前待证问题，哪怕新回复没有成功宣称。

最小优化：从成功 `todo` 工具结果的 `details.phases` 读取完整状态，恢复时与原生状态对齐；只对本轮候选交付回复的宣称对账，保存消息来源，历史宣称保留为历史记录。任务或目标变化时明确 supersede；压缩保留当前未决事实。

### A4 · P2 · 常见失败循环被清零，上游诊断能力尚未接入

[state.ts:275](../src/native/tianshu/state.ts#L275) 的任何成功工具都会清除失败计数。`测试失败 → read 成功 → 同一测试失败` 的探针结果仍为 count=1。正常的读代码、修改、再验证循环因此漏报，建议文本也只剩通用“检查原因、考虑换方法”。

上游已存在可借鉴的职责：`error-diagnosis-hook.ts:118-149` 分类错误并建议具体下一步；`dead-end-detector.ts:109-177` 按文件识别编辑与验证失败循环；`reasoning-spiral-hook.ts:45-91` 识别长推理无行动；`obligation-tracker.ts:42-110` 管理目标证据义务；`problem-attack-hook.ts:117-180` 与 `problem-attack-loop.ts` 登记假设、判别探针、证据与结算。Alpha 当前状态与事件中没有对应入口。

优化方向：先迁入错误分类、按目标的失败循环和未决证据义务，再考虑假设/探针登记。只迁入纯归约与建议语义，使用 OMP 原生事件与 `appendEntry`；由 OMP 自己决定后续动作。验收要求建议具体对应观察到的错误，并能定位其来源。

### A5 · P2 · 代理与 profile 在宿主边界丢失

[launch.ts:50-74](../src/native/launch.ts#L50) 的环境 allowlist 去掉 `HTTPS_PROXY/HTTP_PROXY/ALL_PROXY/NO_PROXY` 与大小写形式，也去掉 `OMP_PROFILE/PI_PROFILE`。纯函数探针确认 proxy、bypass 与 profile 均未保留。

影响：依赖代理的模型/插件/网页网络调用失去原生访问条件；父配置服务按 named profile 读取，但内核 child 可能回到 default profile，造成模型、账号和配置不一致。

最小优化：明确传输配置的 allowlist，代理凭据单独处理；将所有 child 固定到父进程已经解析的原生 agent dir，保证配置目录身份一致。保留原有凭据和调试端口隔离规则。验收使用本机假代理、两个独立 profile 与无凭据断言。

### A6 · P2 · 从终端返回桌面的 Goal/Vibe 恢复不完整

[omp-host.ts:13](../src/native/omp-host.ts#L13) 仅调用 `control.plan.restore()`，后者处理 plan/plan_paused。实际安装的 OMP 中，Goal/Vibe 恢复在 TUI `interactive-mode.ts:4104-4139`，SDK 初始工具还排除 goal。关闭终端后 [server.ts:649](../src/native/server.ts#L649) 自动重建 RPC，却未恢复这些模式的执行语义；持久模式又会阻止进入桌面 Plan。

建议分步处理：先准确展示“该原生模式需要在终端继续”，再接入 SDK 可支持的原生恢复和执行语义。需要真实终端→RPC、冷恢复与工具集合检查；现有模式互斥测试不足以证明恢复成功。本次已核对代码，未做真实 Goal/Vibe 模型运行验证。

### A7 · P2 · shadow 模式仍影响压缩上下文

[extension.ts:92](../src/native/tianshu/extension.ts#L92) 仅抑制消息投递，[session.compacting](../src/native/tianshu/extension.ts#L197) 仍返回 reanchor context。观察模式因此改变模型压缩输入。

最小优化：shadow 只记录状态，压缩钩子不返回上下文。验收同时检查消息、模型上下文和执行行为，而不是仅断言 `sendMessage` 没被调用。

## 保持原生边界的优化顺序

1. **先修契约与证据准确性**：A1、A2、A3、A7；每个问题都有直接可复现条件，改动可单独验证。
2. **释放宿主边界内的能力**：A5、A6；统一配置身份与模式状态，验证 RPC/终端往返。
3. **加强天枢的具体建议**：A4；从错误分类、验证失败循环、目标义务开始，补完整事件覆盖，再接入假设/探针记录。

保守选项是仅修上述确定性问题，维护成本最低，但天枢仍是轻量提醒层。推荐方案是在同一事件桥上逐步增强事实与诊断能力。重新引入另一套执行循环会重复工具、审批、重试和上下文所有权，并偏离既有原生化方向，收益不足以支撑其复杂度。

另有明确的兼容边界：浏览器授权目前覆盖整个 `eval`，拒绝或接管浏览器也会阻止普通求值。这是有意处理持久别名的保守策略；后续可在实际 browser 命名空间调用处授权，或提供不含 browser 的求值上下文。不要用源码关键词匹配替代该边界。

## UI/UX 审查与温润立体方向

### 当前观察

真实隔离预览的首页与设置已在内置浏览器查看并保存。界面没有缺少圆角：常用圆角已有 8/10/12/16px；输入框也有阴影。但主画布纯白、侧栏平面蓝灰，阴影缺少统一光源与“接触/悬浮/模态”的区别，组件主要呈现在同一平面上。

| 问题 | 影响 | 建议 |
| --- | --- | --- |
| 主区与侧栏主要靠直线分隔 | 整体像平面面板，缺少承托感 | 主内容使用温润表面与柔和边缘，侧栏作为后层 |
| 输入框阴影与边框缺少厚度关系 | 主交互仍显单薄 | 上缘受光、底缘厚度、接触与扩散两层阴影 |
| 天蓝按钮平涂，反馈只有颜色变化 | 主操作缺少材质和触感 | 低饱和蓝的受光渐变、底边、hover 与按压位移 |
| 菜单/浮层和普通表面层级未统一 | 分组关系依赖边线 | 固定光源，菜单高于输入框，抽屉与模态最高 |
| 设置默认连续展示 15 种原生模型角色 | 常用账号信息需要长距离查找 | 默认模型和账号先呈现，其余角色用可展开区域保留 |
| 部分按钮只提供小图标 | 新用户需要猜用途 | 常用入口保持可见名称，窄窗口保留标签/提示与焦点 |

### 设计原则与具体范围

保留蓝灰品牌，浅色用温润灰白背景与明亮承托表面，深色用灰蓝的表面明度、上缘微光和阴影区分深度。文案保持清晰、亲切。立体感集中在有意义的交互表面：

- 底层：背景与侧栏。
- 主工作面：内容、设置和文件区域，使用柔和圆角与统一受光方向。
- 操作面：输入框、新会话与文件卡片，显示接触阴影与少量厚度。
- 高层：模型菜单、抽屉、对话框，使用更宽的扩散阴影与焦点管理。
- 主按钮：低饱和蓝、顶部微光与底部厚度，hover 上浮约 1px、按压约 2px；禁用状态维持清晰的非交互感，减少动态效果设置下关闭位移。

已落实到 `desktop/ui/src/styles/tokens.css`、`desktop/ui/src/app/NativeApp.css` 的共享材质与状态；首页文案同步 `NativeHome.tsx` 与英文词表。保留现有组件、路由、模型/账号/Skill/本机能力入口。模型角色的渐进展示仍为后续建议，未在本轮改动。

预览可切换首页、会话、设置、浅深主题，并与当前真实首页截图比较；全部示例内容均为设计展示，按钮不调用模型或后端。交互预览呈现在本次对话中；本机检查文件为 `artifacts/dual-core-ux-audit-2026-10-01/design-preview.html`。
