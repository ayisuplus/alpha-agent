# 任务状态机重构开发计划（参考 deepseek-harness）

日期：2026-09-28。本计划供后续接手的开发者或智能体执行；每个阶段独立成一个 PR，按 [AGENTS.md](../AGENTS.md) 的规范交付。背景数据来自同日的 [Harness 修复与评测](harness-fixes-eval-2026-09-28.md)。

## 一、结论先行

- Alpha 的"认知虚拟机"名字来自天枢（Tianshu）的 CVM，但现在只继承了它的一条原则和三个结构：**确定性的运行时监管概率性的模型认知**；任务契约（TaskContract，版本化目标）、证据门禁（Evidence，运行时而非模型判定完成）、收敛检测（Convergence，无进展则停止）。天枢的认知帧（Cognitive Frame）、认知镜像（Cognitive Mirror）、测量—归一—评估外环都没有实现。说"已经没什么关系"是准确的；建议保留原则，不再沿用 CVM 这个名字，改称**任务状态机**。
- 值得借鉴的是 deepseek-harness（下称 dsh，MIT 许可）的**状态建模方式**，而不是它的插件框架。核心只有一句：**只追加的事件日志是唯一事实来源，所有状态都是日志的投影；模型看到的一切都能从日志重建。**
- 本周评测暴露的问题（任务卡在"需要输入"、审查子实例不返回结果、并行会话互相覆盖、审批暂停原因不清）都和"状态分散、转换隐式"有关。重构目标是让每个状态、每次转换、每个暂停原因都是显式的、可回放、可测试的。

## 二、现状

### 状态存在哪里

| 存储 | 内容 | 形式 |
|---|---|---|
| `TaskLedger`（`.alpha/tasks/<id>.json`） | 目标与版本、验收项、证据、状态、阶段、认知修订（步骤、缺口、子代理、实例、Skill 提案）、每轮运行、目标续跑、开发审查、子代理请求、检查点 | **整文件可变快照**，886 行代码、48 个修改方法；写入前比对整文件哈希防并发覆盖 |
| 活动日志（`activity/<id>.jsonl`） | 时间线展示用的状态、工具、文本 | 只追加，但不是事实来源 |
| OMP 会话（`omp/sessions`） | 模型实际看到的对话 | OMP 自己的格式；账本里的认知快照每轮重新拼进提示词，**模型看到了什么无法从账本重建** |
| 其他 | 操作日志、项目状态回合、队列、自动化、命令审批、网页授权、子代理信箱、子代理工作区状态、源码快照、证据文件 | 各自一套文件格式 |

### 状态怎么变

- `status`（active / needs-input / stopped / complete）在 9 处赋值，`phase`（plan / plan-review / execute）在 5 处赋值，没有集中的转换表；非法转换靠各方法里的零散检查挡住。
- 暂停原因是一段自由文本加一个 `blockedService` 字符串，界面和恢复逻辑都要猜。
- 子代理实例状态、审查结果、子代理请求分别存在认知记录的不同字段里；"审查子实例没有返回结果"只能表现为任务暂停。

### 本周评测里与状态有关的问题

| 现象 | 根因 |
|---|---|
| 3 个任务代码正确，却停在"需要输入" | 暂停原因不分类型：等待命令审批和"审查未返回"都是同一个 needs-input |
| 审查子实例反复失败后不提交结果 | 子代理结束时没有强制的结果事件；缺结果不是一个可处理的状态 |
| 并行任务启动时会话互相替换 | 进程内共享的隐式身份（已修复，但说明身份需要显式建模） |
| 同一任务耗时相差 10 倍 | 无法从记录回放当时模型看到的上下文，只能猜原因 |

## 三、从 dsh 借鉴什么

依据 dsh 仓库的 `docs/architecture.md`、`docs/agent-lifecycle.md`、`docs/subsystems/{goal,plan,subagent,agent-team,invariants}.zh.md`（2026-09-28 阅读）。

| dsh 的做法 | 对 Alpha 的意义 | 采用 |
|---|---|---|
| 会话是只追加的 `SessionEvent` 日志，状态由 `deriveMessages()` 等纯函数投影得出 | 账本从可变快照改为事件日志 + 折叠 | ✅ 核心 |
| "模型可见即记录"（Model-visible means logged），运行时检查请求能否从日志重建 | 每一步把拼给模型的任务上下文记成事件 | ✅ |
| 回合 / 步骤结构（`turn/start` → `step/start` → … → `turn/end`），持久事件与实时事件分开 | Alpha 的"运行"细分为步骤；时间线直接读持久事件 | ✅ 简化版 |
| 目标是带修订号的快照（`GoalRef` = id + revision），比较并交换更新；完成与阻塞由运行时判定；`maxGoalRounds` 限制续跑轮数；每次变化写 `goal/change` 事件 | 与 Alpha 的目标续跑对齐，改为事件 + 修订号 | ✅ |
| 计划模式是一个事件（`plan/mode`），**只改提示词段落，不改工具目录** | Alpha 规划期换一套工具，可以评估是否改为只换提示 | ⚠️ 评估后决定 |
| 子代理有 `subagent/descriptor` 事件、最多一个常驻激活（Activation）、冷恢复；结果带 `stopReason`（completed / aborted / error / max-tokens / refusal） | 子代理"没返回结果"变成一个明确的停止原因，由主代理处理 | ✅ |
| 团队任务板：DAG，每个任务带修订号、比较并交换；信箱可由"已排队减已送达"重建 | Alpha 的计划步骤和信箱改为同样的事件 + 修订号 | ✅ |
| 会话格式有版本（`session.vN.jsonl`），每个迁移包只负责一步 `vN → vN+1` | 账本格式版本化，旧账本可迁移 | ✅ |
| 每个包自带不变量检查（`InvariantError`，稳定错误码） | 状态机不变量集中定义，测试和开发模式下每次追加都检查 | ✅ |
| Cordis 插件框架、多种子代理后端、ACP / SDK 等 | 与 Alpha 基于 OMP 的架构不符，改造代价远大于收益 | ❌ 不采用 |

许可：dsh 为 MIT，可参考实现，引用代码时保留版权声明；天枢的理论文档为 CC BY-NC-ND 4.0，只借鉴思想，不复制文字。

## 四、目标设计

### 4.1 任务事件日志

- 位置：`.alpha/tasks/<id>/events.v1.jsonl`，每行一个事件：`{ seq, at, type, actor, payload }`。`seq` 从 1 连续递增；`actor` 为 user / runtime / coordinator / worker:<id> / reviewer。
- 追加使用**序号比较并交换**：写入方声明期望的上一个 `seq`，不符则拒绝并要求重新折叠。取代现在的整文件哈希比对，支持主进程和子代理进程并发写入同一任务。
- 每 N 个事件（建议 200）写一个快照 `snapshot.<seq>.json` 加速加载；快照只是缓存，删掉可从日志重建。
- 现在的 `<id>.json` 保留为**投影**：每次追加后重写，兼容所有现有读取方（界面、自动化、脚本），直到它们迁移完。

### 4.2 事件类型（首批）

| 类别 | 事件 |
|---|---|
| 契约 | `task/created`、`contract/revised`、`criteria/set`、`guidance/recorded`、`input/attached` |
| 阶段与状态 | `phase/changed`、`status/changed`（带原因码，见 4.4） |
| 运行 | `run/started`、`step/context`（本步给模型的任务上下文摘要与哈希）、`run/ended`（结果、用量、固定提示词体积） |
| 证据与审查 | `evidence/recorded`、`review/recorded`、`preview/published`、`checkpoint/committed` |
| 目标 | `goal/changed`（完整快照 + 修订号） |
| 计划 | `plan/submitted`、`plan/approved`、`plan/revised`、`step/changed`（计划步骤，带修订号） |
| 子代理 | `worker/descriptor`、`worker/activated`、`worker/result`（带 `stopReason`）、`worker/request`、`worker/request-resolved`、`worker/integrated` |
| 人机交互 | `input/requested`、`input/answered`、`approval/requested`、`approval/decided`、`question/asked`、`answer/recorded` |

### 4.3 状态折叠与转换表

- `foldTask(events): TaskState` 是纯函数，严格校验：序号不连续、非法转换、修订号倒退都抛出带稳定错误码的错误。
- 状态转换集中在一张表里（当前状态 × 事件 → 新状态），例如：

| 当前 | 事件 | 新状态 | 条件 |
|---|---|---|---|
| active / execute | `status/changed → complete` | complete | 所有验收项都有当前版本的通过证据；无待集成子代理；无待处理请求 |
| active | `input/requested` | needs-input（原因码） | — |
| needs-input | `input/answered` / `approval/decided` | active | 原因码与回答类型匹配 |
| complete | `contract/revised` | active / execute | 版本号加一，旧证据失效 |
| active / plan | `plan/submitted` | active / plan-review | 计划非空 |
| active / plan-review | `plan/approved` | active / execute | 修订号与提交时一致 |

- `TaskLedger` 现有的 48 个方法改为"校验 → 生成事件 → 追加"，对外接口不变，便于逐步迁移。

### 4.4 暂停原因码

`status/changed → needs-input` 必须带原因码和可执行的恢复动作，界面据此显示按钮而不是一段文字：

| 原因码 | 含义 | 恢复动作 |
|---|---|---|
| `approval` | 命令或网页动作等待批准 | 批准 / 拒绝 |
| `question` | 模型向用户提问 | 回答 |
| `worker-no-result` | 子代理结束但没有结果 | 重派 / 由主代理直接审阅 / 忽略该子代理 |
| `sandbox` | 沙箱不可用 | 查看诊断 / 改权限模式 |
| `model` | 模型不可用 | 换模型 |
| `project-state` | 项目目录或检查点异常 | 重新检查 |
| `capability` | 专家或 Skill 缺失 | 安装 / 跳过 |
| `budget` | 预算用尽 | 追加预算 |

其中 `worker-no-result` 默认**不暂停任务**：主代理收到 `worker/result`（`stopReason = no-result`）后自行决定，只有它也无法处理时才升级为暂停。

### 4.5 模型可见即记录

- 每一步把拼进系统提示的任务上下文（认知快照、验收缺口、专家人设哈希、Skill 快照、固定提示词体积）记成 `step/context` 事件；大块内容存为按哈希寻址的文件，事件里只放哈希。
- 新增 `bun run replay <taskId>`：按事件重建每一步的任务上下文，并与 OMP 会话对照，回答"当时模型看到了什么"。
- 开发与测试模式下的不变量：每个 `run/started` 之后必须有 `step/context`；提示词中的任务上下文哈希必须与事件一致。

### 4.6 不变量（首批）

1. `seq` 连续且只增不减；每个事件都能被折叠。
2. 同一任务同一时刻最多一个进行中的运行（与操作管理器的任务锁一致）。
3. `complete` 时，所有验收项在当前契约版本和当前源码版本下都有通过证据。
4. 契约版本单调递增；修订后旧证据全部失效。
5. 子代理结果只能来自已激活的子代理；集成只能针对已返回的结果。
6. 每个 `needs-input` 都有原因码，且有与之匹配的恢复事件类型。
7. 目标、计划步骤、团队任务的修订号单调递增，比较并交换失败不产生事件。

## 五、分阶段计划

每个阶段都要求：`bun run check`、`bun run test` 全部通过；改动专家包时另跑 Skill 校验；阶段结束写入 `docs/` 带日期的说明。

### P0 基线与护栏（1–2 天）

- 为现有账本行为写特征测试：取 `.alpha/tasks` 中若干真实账本的**副本**（不改用户数据），记录每个修改方法调用前后的状态，作为重构后的对照。
- 把第 4.6 节的不变量写成可执行检查，先对现有账本运行，记录哪些已经被违反（这是发现存量问题的机会）。
- 评测基线：`bun run eval` 每个任务重复 3 次，记录成功率、自评与独立检查的偏差、用量中位数。
- 交付：特征测试、不变量检查脚本、基线报告。

### P1 事件日志与折叠（3–5 天）

- 新增 `src/runtime/task-events/`：事件类型、序号比较并交换追加、快照、`foldTask`、转换表。
- `TaskLedger` 内部改为追加事件，并**双写**现有 JSON 投影；对外接口与行为不变。
- 迁移：读取旧 JSON 账本时生成 `task/imported` 事件（完整快照），之后正常追加；旧文件保留备份。
- 验收：全部现有测试通过；P0 特征测试逐字节一致；对真实账本副本"导入 → 折叠 → 投影"的结果与原文件一致；并发写入测试（两个进程各追加 100 个事件）无丢失。
- 风险：48 个方法逐一改造工作量大，按"读多写少"的顺序迁移，每迁一组跑一次特征测试。

### P2 状态与暂停原因显式化（2–3 天）

- 状态与阶段只能经由转换表改变；删除散落的直接赋值。
- 实现第 4.4 节原因码；界面按原因码显示恢复按钮；时间线直接读持久事件。
- 目标续跑改为 `goal/changed` 快照 + 修订号（对齐 dsh 的 goal）；无进展停止写成带原因码的事件。
- 验收：评测中"独立检查通过但自评未验收"的任务都能从事件看出原因码；`worker-no-result` 不再直接暂停任务。

### P3 子代理生命周期（4–6 天）

- `worker/descriptor`（工单、专家快照、Skill 快照、能力）、`worker/activated`、`worker/result`（`stopReason`）写入父任务日志；子代理自己的状态仍在其工作区，但父任务只信事件。
- 信箱改为事件：已排队减已送达即可重建，重启后不丢消息。
- 计划步骤改为带修订号的任务板（可参考 dsh 的 agent-team 任务 DAG），子代理认领、完成都走比较并交换。
- 验收：杀掉服务器进程再重启，进行中的子代理、未送达消息、计划步骤都能从事件恢复；构造"子代理不提交结果"的测试，主代理得到 `no-result` 并继续。

### P4 模型可见即记录（3–4 天）

- 实现第 4.5 节：`step/context` 事件、按哈希存储大块内容、`bun run replay`。
- 评测报告里增加"每步上下文体积"和"首次响应延迟"，用于解释耗时差异。
- 验收：任意一次评测运行都能用 `replay` 重建每一步的任务上下文，哈希与当时一致。

### P5 附属存储收拢（按需，2–5 天）

- 逐个评估操作日志、项目状态回合、队列、自动化、命令审批、网页授权：能归入任务事件的（审批、授权、项目回合）归入；属于全局的（队列、自动化）保持独立，但同样改为事件 + 投影，并写入 `docs/` 的持久化清单（参考 dsh 的 `persistence-catalog`）。
- 验收：每种持久化文件都有格式版本、迁移路径和一句话说明。

### P6 评测验证（持续）

- 每个阶段合并前后各跑一次评测（每任务 3 次），比较成功率、偏差、用量中位数。
- 扩充任务：加入更难的代码任务（例如 SWE-bench Verified Mini）和需要多轮暂停恢复的任务，专门测试状态机。

## 六、交接说明

- 顺序：P0 → P1 → P2 是主线，必须按序；P3、P4 可在 P2 之后并行；P5、P6 按需。
- 每个阶段一个分支、一个 PR；PR 描述写清改了哪些事件类型、迁移方式、验证结果。
- 不改用户数据：所有针对真实账本的测试都用副本；迁移首次运行前自动备份 `.alpha/tasks`。
- 评测会真实调用模型并消耗额度；跑之前先 `bun run eval --selfcheck`，并注意多个评测同时跑会互相拖慢模型响应。
- 测试不会触发沙箱弹窗（`bunfig.toml` 预加载已关闭真实沙箱）；评测第一次用到只读检查时可能各弹一次安装窗口（最多 3 次）。

## 七、待决定

1. 规划阶段是否像 dsh 一样**不换工具、只换提示词**：好处是模型行为更稳定、提示缓存命中更高；代价是规划期模型能看到写入工具，需要靠运行时拒绝。建议 P2 后用评测对比再定。
2. 是否正式放弃"认知虚拟机"的名称，统一称"任务状态机"，并在 `docs/dynamic-experts-and-cognition.md` 中说明与天枢的关系。
3. 事件日志是否同时承载子代理的完整会话（dsh 的做法），还是只记描述、激活与结果（本计划的建议，改动更小）。
