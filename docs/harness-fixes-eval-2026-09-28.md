# Harness 修复与评测（2026-09-28）

承接对 Alpha harness 的评估（可靠性与安全边界强，简洁度和评测闭环弱），本轮先做评估里提出的三项修复，再建立评测集并用它测试。评测过程中又发现并修复了 7 个问题，其中 1 个是本机环境问题，需要用户决定。

## 一、评估中提出的修复

| 项 | 改动 | 位置 |
|---|---|---|
| 按任务类型的分支收拢 | 5 种任务类型之间的 12 项差异（交付工具、附件、命令、派发、专家视角、第三方插件、Office 工具、开发审查、代码验收、上传目录保护、验收方式、是否写代码）集中到一张表；运行器、会话装配、账本、路由、插件、CLI 都改为查表。删除 `isGeneralWork` | `src/runtime/task-profile.ts` |
| 验收策略拆分 | `runs.ts` 里 150 行的按类型验收分支拆成四个策略：网页预览、代码检查、交付文件、自适应（通用任务）。构建、预览发布和浏览器验收移到独立模块，路由从那里引用。`runs.ts` 从 690 行降到 483 行 | `src/server/acceptance.ts`、`src/server/verification.ts` |
| 固定提示词体积 | 每次运行记录系统提示词和工具定义的 token 数（用 OMP 的分词器）及占模型上下文的比例，写入运行记录；超过 20% 时在时间线提示 | `src/runtime/prompt-budget.ts` |

用一张测试把重构前后每种任务类型主代理拿到的交付工具钉住，确认行为没变。

## 二、评测集

`eval/` 下 8 个任务（5 个代码、3 个通用），评测脚本像用户一样通过 HTTP 接口派任务，等 Alpha 自己结束，再用它看不到的检查打分：代码任务跑隐藏测试，通用任务检查回答或逐行比对生成的文件。每个隐藏测试都经过自检：在原始代码上失败、在参考解法上通过。用法见 `eval/README.md`，`bun run eval`。

模型为默认的 MiMo-V2.6-Flash；本轮全部评测运行共消耗约 1,280 万 tokens（含旧版本对照和复测）。

## 三、评测中发现并修复的问题

| # | 问题 | 证据 | 修复 |
|---|---|---|---|
| 1 | 通用任务的"是否要求交付文件"按关键词判断，不识别否定："不需要生成文件"被当成要求文件，正确回答被判失败 | `sales-question` 回答正确，Alpha 记为失败 | 按分句判断，含"不需要/无需/不用/不要"等的分句不计 | 
| 2 | **沙箱弹窗**：只读子实例每次检查都复制到新临时目录，沙箱按目录建配置，新配置首次使用要管理员权限安装，于是每次检查弹一次窗 | `%LOCALAPPDATA%\Alpha\sandbox-profiles` 累积 104 个配置（约 142 MB），每个只用过 1 次；日志中"需要安装"与"开始安装"之间 8 秒即用户点击弹窗 | 只读检查改用 3 个固定槽位（跨进程加锁，用后清空但保留目录），每台机器最多安装 3 次；修复后同一配置被复用 13 次、只安装 1 次 |
| 3 | 测试套件调用真实沙箱，每次完整跑测试都会弹窗并写入用户目录 | 配置按测试运行时间成批出现 | 测试预加载关闭真实沙箱（命令一律失败关闭，不会不受限运行），槽位和配置放临时目录；修复后完整测试新增配置数为 0 |
| 4 | 审查子实例把整条命令（`bun test test`、`npm test`）当检查名传给 `alpha_check`，全部被拒，无法验证 | 子实例会话记录 | 允许按脚本名、`bun/npm run <名>` 或脚本原命令指定检查，仍只运行已配置的命令；工具说明和错误信息列出可用检查名 |
| 5 | **并行任务同时启动会互相替换**：OMP 在进程内以默认 ID "Main" 登记每个会话 | 3 个任务同时启动，其一立即报 `Agent "Main" was replaced during session initialization` | 每个 OMP 会话使用唯一 ID（运行、命令审查、标题、提示词优化四处）；4 个任务同时启动复测，0 次冲突 |
| 6 | 任务为试运行临时脚本调用 `alpha_command`，每条都要用户批准，任务因此暂停 | 暂停原因依次为 `node -v`、`bun run smoke.ts`、`python summarize.py` | 代码任务提示改为"在已配置的测试里补测试再用 alpha_check"；通用任务提示"命令要等批准，小型数据和文件工作直接读输入、写结果" |
| 7 | 沙箱不可用时，审查子实例反复重试 `alpha_check`，最后不提交结果，任务因"审查未返回结果"暂停 | 子实例最后一串调用全是同一错误 | 沙箱不可用时明确告诉子实例不要重试、直接审阅源码并在结果中说明检查未能运行；同一会话不再重复探测 |

### 本机环境问题（待决定）

Alpha 在运行沙箱命令前会做隔离探测。本机上 Codex 离线沙箱**无法阻止回环网络**：防火墙已开启、4 条 Codex 屏蔽规则都已启用，沙箱进程仍能连上本机端口，探测报"联网未被拒绝"，Alpha 按设计拒绝在沙箱里运行检查（失败关闭）。用户真实数据里已有 8 次同样的记录，不是本轮引入的。这影响审查子实例的检查，以及直连项目在"询问/自动"权限下的命令。可选方案需要用户决定：保持现状（安全但这些检查无法运行）、排查本机防火墙对回环流量的处理，或把"只放行回环、仍禁止外网"作为可接受的隔离级别（会削弱对本机服务的隔离）。

## 五、结论与局限

- **成功率看不出差别**：两个版本都是 8/8。任务偏简单，出现了天花板效应；要比较版本需要更难的任务（例如 SWE-bench Verified Mini）。
- **成本不能下结论**：当前版本合计 tokens 约为旧版本一半，但差距主要来自旧版本两次异常长的运行；其余 6 个任务上当前版本反而多用约 30%。同一版本同一任务的耗时可相差 10 倍，单次运行的噪声大于版本差异。
- **评测最大的价值是找问题**：自评与独立检查的差异（"漏判"）直接指向了 7 个真实的 harness 问题，它们都不会让代码写错，但会让任务无谓地停下、失败或打扰用户。
- **固定提示词约 9.7k tokens**（系统约 4.9k、工具约 4.7k），不到当前模型上下文的 1%。
- **并行会拖慢模型响应**：多个任务同时调用同一账号时，单步响应出现过 12 分钟的空档。并行上限应结合模型额度设置，默认的 3 在这个额度下偏高。
- 下一步：每个任务重复 3 次取中位数；加入更难的任务；接入公开基准。
