# 动态专家协作

Alpha 使用 TaskLedger 保存任务目标、验收证据、认知修订、子代理身份、每轮运行与 Skill 提案。任务开始时有初始认知；模型可通过 `alpha_plan` 修订候选专家和步骤。候选名单只用于计划；`alpha_spawn` 派发工单时才创建子代理。一个子代理有稳定 ID、任务角色、局部认知记录和独立 Git worktree；匹配的版本化专家人设和 Skill 优先使用，但不是派发前提。找不到合适专家时，主代理可派发中性子代理，工单必须有明确目标、源码范围和验收标准。每次执行另有运行 ID；`alpha_continue` 在同一会话和工作区继续它，可为下一轮切换调查、实施或审查模式。主代理按运行 ID 检查实际差异，逐个决定是否集成。按独立任务派发，不按单个错误派发。

认知虚拟机由任务状态和固定的角色思维规则组成。主代理对用户的整体目标、取舍、集成和最终验收负责，也可直接完成简单任务；子代理对工单范围内的专业判断、验证和影响上报负责。规划与执行会话使用主代理规则，隔离工单与独立审查使用子代理规则。规则版本写入运行记录；专家包只补充专业方法，不能改动角色责任、权限或验收门禁。

主代理派发工单须写明理由。子代理发现错误前提、范围外影响或能力缺口时，使用消息箱发送事实、当前源码的精确片段或本轮检查凭据及建议；请求发送成功后，本轮以 `needs-context` 交回主代理，回复后再续跑。未获回复的请求阻止其将工单标记完成。主代理检查消息、工单结果和实际差异后，记录集成或拒绝理由。工单、消息和实例记录沿用任务契约版本、源码版本与运行 ID，不保存模型的完整内部推理。历史记录缺少新字段仍可读取，下一轮运行应用当前角色规则。

调查和审查模式只读；已配置检查在沙盒中的临时源码副本上运行。最终源码审查由独立子代理在 worktree 中执行；有合适审查专家时优先使用，否则使用中性审查角色。审查通过需要引用当前源码原文；结论只绑定到审查时的任务契约和源码版本。源码或契约变化后重新审查。审查提出的修复优先交回原实施子代理，最多自动修复两轮。

子代理只向主代理的任务消息箱发送信息和请求，不能直接联系其他子代理。主代理读取消息后决定回复、转发、继续某个子代理或向用户请求输入。消息记录发送者、运行、接收者、任务契约和源码基线；运行中消息在会话安全边界提醒接收方，读取后显式确认。重复调用使用同一消息 ID，旧运行和旧任务版本的消息在界面中标记。此通信只传递信息，不改变权限。该中心化路由参考 [Orca 的编排文档](https://github.com/stablyai/orca/blob/d443320af2c5152cea38a3efc451a0a80c5c5550/docs/site/content/docs/cli/orchestration.mdx)。

Alpha 管理的生成/复制工作区在首次派发时会建立本地空 Git 锚点。直接打开的项目必须本身是已有提交的 Git 仓库根目录；否则派发会明确提示，最终审查等待该条件满足，不会改动用户目录的 Git 状态。

专家库只保存用户添加的专家。旧的前端、后端、设计和测试预设作为可选模板展示，不会自动加入。新建或编辑的专家保存为版本化专家包：`PERSONA.md` 记录人设与专业方法，`skills/` 保存选择的已安装 Skill 的完整只读快照，清单记录内容哈希。用户可在新任务中明确指定专家；该选择必须保留在计划中，而且要有实际完成的专家实例才算满足。旧版 JSON 专家仍可读取，修改后生成专家包。

专家包位于任务数据目录的 `expert-packs/`，不会安装到全局或内置 Skill 目录。共享能力目录以带专家来源的独立 ID 索引其随包 Skill；相同名称的 Skill 保留不同来源和内容哈希。专家的人设与 Skill 只是推荐组合，受管代码工单仅装载主代理显式选择的能力，其他专家工单也可选择该 Skill。停用或删除原插件不会改变已打包版本。执行模式和工具权限仍由运行时决定；专家文本和随包 Skill 都不能增加权限。计划修订读取当前已启用的专家和可用 Skill；已经派发或完成的步骤不能被修订改写。已经派发的工单保留专家、源码和 Skill 快照；专家库后续修改不改写历史实例。

开发任务通过 `runDevelopmentWorkflow` 调度。主代理处理待集成结果和消息后，独立审查子代理检查实际源码和任务要求，提交 `pass`、`changes-requested` 或 `inconclusive`。任务完成仍需要同一契约和源码版本的实际验收证据。

Worker 是有稳定身份的任务级子代理，不是专家类型，也不是一次运行。认知虚拟机持有任务全局计划；专家包是可选的专业增强；子代理认知保存已验证依据、待解决问题与下一步，每轮运行另存结果和预算。失败或取消的运行保留工作区快照，下一轮沿用基线和已有改动；协调轮预算到期时记录状态并续跑，任务总预算仍是上限。主代理负责计划、消息路由、差异集成与验收。CLI 的 `run-code`、恢复执行和服务器代码任务共用代码验收门禁；多段任务文本使用 `--brief-file <path>` 传入，避免脚本入口截断换行内容。

本地 WorkBuddy experts 可用 `bun run scripts/import-workbuddy-experts.ts <marketplace-dir> <data-root>` 导入。导入器只把各插件顶层 `agents/*.md` 作为专家；位于 Skill 内的 `agents/` 文件保留为随包资源。插件清单声明的 Skill 复制进该专家的版本包，不启用原插件的 Hook、MCP，也不进入全局 Skill 目录。重复导入保留用户后续编辑过的同 ID 专家。初始提示只给出少量候选，需要其他专业时用 `alpha_expert_search` 查询元数据。

所有实例都有 `alpha_browser`。协调实例和最终审查使用当前任务的本地预览；隔离 Worker 的浏览器调用通过独立请求记录转发至主侧同一适配器，并串行执行，导航仍受预览来源限制。没有连接预览时明确返回不可用，不能凭模型描述完成视觉验收。实施模式可在独立 worktree 中读写、构建、运行已配置的低风险检查并读取选中的 Skill。受管代码 Worker 可使用明确分发的内置插件工具和经宿主转发的 MCP 工具；MCP 仍受逐项权限和回执约束，服务凭据不进入 Worker。调查和审查模式不能写入源码或读取已知凭据路径。

主代理通过 `alpha_capability_search` 查询已安装 Skill、MCP 服务和内置工具的元数据；查询不连接服务。主代理可用 `alpha_skill_read` 按目录 ID 读取 Skill，用 `alpha_capability_mcp` 按需打开一个 MCP 服务、列出工具并在逐项授权后调用。`alpha_spawn` 将所选能力及版本快照写入工单。子代理通过 `alpha_send` 上报能力、上下文、权限或项目依赖缺口后立即结束本轮，主代理用 `alpha_worker_resolve` 增配、回复、安装或拒绝。安装使用原任务的精确命令审批，在子代理原工作区的新一轮源码快照后、模型运行前执行；回执、安装产物可用性、运行 ID 和上下文版本写回 TaskLedger，清单及锁文件变化留待主代理审查集成。审批等待、失败和不确定结果不触发未经核实的重复安装。重启后按账本中的请求和回执继续协调，不新建第二套认知状态机。

`alpha_gap` 记录方法、工具、权限或上下文缺口。方法缺口可以使用通用公开技术词查询 skills.sh；结果只作为提案。提案包含 GitHub 仓库、精确提交、`SKILL.md` 路径及其声明的工具、服务和冲突要求。用户批准后，仅复制该提交中的目标 Skill 目录及其资源，并保存内容哈希以检查后续重用。搜索接口属于外部实验性依赖：服务不可用或结果无法精确定位时显示原因，不切换到其他在线来源。

Skill 可以在 frontmatter 中声明 `requires-tools`、`requires-services` 和 `conflicts-with`。派发前检查这些显式要求；工具执行时再次按模式检查权限。运行时不会把 Skill 中的文字当作授权。

内置开发流程借鉴了 [Superpowers 的 subagent-driven-development](https://github.com/obra/superpowers/blob/main/skills/subagent-driven-development/SKILL.md)：给独立任务清晰的工单、由主代理处理中途问题、每轮检查结果并在集成前审查。参考的本地版本为提交 `5bf4e78011075bcfc0dc295f0724994cd123ee71`，其许可证为 MIT、Copyright © 2025 Jesse Vincent。Alpha 没有复制它的固定 Subagent 设定、Hook 或提示模板；已安装的历史包仍保留在原位置，但新任务不装载其外部流程。

## 术语表（2026-09-29 梳理）

子代理与专家的边界只有一条：**专家提供知识，子代理负责执行，交点只有派发工单时的一次绑定**。统一词汇：

| 术语 | 含义 | 曾用名 / 历史拼法 |
|---|---|---|
| 专家（expert） | 版本化知识包：人设 + 方法 + 随包 Skill 快照。绑定专家只装载其人设；Skill 与能力（MCP/内置工具）一律显式选择 | 代码旧名 `AgentPreset*` 已统一为 `Expert*`；`preset`/`agent-preset` 皆指专家 |
| 子代理（worker） | 任务级执行身份：稳定 `agentId` + 执行模式 + 绑定的专家快照 + 轮次（`instanceId`）+ 结果与消息 | 旧文档混用 worker/subagent/agent/instance：instance 现在只指一轮执行 |
| 执行模式（mode） | 权限：`investigate`/`review` 只读，`implement` 可写源码 | 原与"角色"混用 |
| 会话角色（session role） | 运行形态：`coordinator`/`worker`/`reviewer`/`planner`/`answer` | 原与"角色"混用；worker 提示词里的 "Selected role" 已改为 "Assigned expert" |
| 绑定契约 | 同一个"指定专家"入口，两种契约：`web-product`/`code-change` 是**执行契约**（必须有该专家完成的实例，`task-completion` 的 `designated-expert` 缺口 + `worker-binding` 的分配守卫）；其余类型是**专家视角**（仅作主代理人设，不要求实例） | 见 `task-profile.ts` 的 `expertPerspective` 注释 |
| 派发 | 单一入口 `alpha_spawn` → `worker-binding.ts`（计划一致性 → 指定专家分配 → 绑定 → Skill 要求校验） | 旧的 `alpha_delegate` 双轨已删除 |

存储与数据的历史拼法（有意保留）：`.alpha/agent-presets.json` 文件名与其 `format: "agent-presets"` 标记、`presets/agents/index.json` 的 `presets` 键、`.alpha/expert-packs/`（专家包只做版本快照，人设以注册表数据为准）。
